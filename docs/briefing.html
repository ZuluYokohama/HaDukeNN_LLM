OODA

Observe

The feasibility record counts units on the valid split against GPT-2 BPE: 181,544 versus 249,887 (27.35% fewer), byte fallback 0.048%, build 0.093 CPU-hours, peak RAM 4.83 GB, vocabulary size 65,536. That record is metadata. It is not the text it was counted on.

Orient

The written G0 cap is V ≤ 64,000. 65,536 is 2^16, which is also called 64k in some tokenizer names. The harness does not treat those as the same number. G0 is therefore partial: four limits hold, and the vocabulary line does not. G1, the units-only pilot, failed both tests: hnt64k test BPB 1.452254 is above struct32k plus one standard deviation (1.329303), and train FLOPs/byte 3.5706e7 is above struct32k and sw64k. G1b, the structured hnt40k follow-up, also failed on BPB: test BPB 1.477304 is still above 1.329303. Its train FLOPs/byte 1.1929e7 is about 61% below struct32k, so only the FLOPs side moved. G1c ran hnt40k-struct-v2 compute-matched to 4.2006e15 train FLOPs, n=3, on WikiText-103. Test bits per byte are 1.269376 ± 0.004417 at 1.2061e7 train FLOPs per byte. The sw40k-struct-v2 control is 1.322698 ± 0.006710, struct32k is 1.322354, and the GPT-2 tokenizer arm is 1.328219. hnt versus that control is -0.0533 (p 7.1e-4). The hnt mean is under the G1 line of 1.329303. G1c passes as a compute-matched comparison. g1d retrained struct32k on 348.3M bytes, the same train bytes hnt saw, and scored 1.194155 ± 0.000824 at 1.0756e16 train FLOPs. That beats hnt by 0.075 at equal data, so G1c is a compute-efficiency win, not a per-byte modeling win. g1g, hnt40k-struct-v2 FLOPs-matched to g1d at 1.0756e16 train FLOPs, scored 1.174315 ± 0.000564 (seeds 1.174805, 1.173698, 1.174444). That is 0.019839 below g1d (Welch p 1.3e-5), That is a win at equal analytic train FLOPs only (the 6N + attention + head count). The structured model swaps the flat 40k output softmax for a factored cluster-then-unit head (200 clusters × 200 units). At d=384 the flat head is about 56.6% of plain-model FLOPs per token, so struct-v2 counts about 2.22× fewer FLOPs per token. At equal FLOPs, g1g therefore saw 891.7M train bytes (about 1.65 epochs, against g1d's 0.64), and it took about 1,488 s per seed against about 501–505 s for g1d and g1h, so it is about 3× slower on wall clock. g1h, plain hnt40k with the structured path off (struct none, mean compose, low-rank residual, no spectral init) at the same 1.0756e16 train FLOPs, scored 1.197637 ± 0.000517 (seeds 1.198146, 1.197111, 1.197653). That is 0.023321 above g1g (p 8.4e-7) and 0.003482 above g1d (p 0.006): at equal analytic FLOPs and the same tokenizer, the structured run scores lower, but it also saw about 2.2× the data. At equal data the order reverses. G1c, the same hnt40k-struct-v2 model at 348.3M train bytes, is 1.269376 ± 0.004417. That is 0.0579 worse than plain hnt40k at the same bytes (g1i, Welch p 8.8e-5) and 0.0752 worse than struct32k (g1d, p 8.2e-4). The mechanism resembles a class-factored softmax (Goodman 2001, arXiv:cs/0108006). This is not evidence that the structure layer models text better. Wall-clock-matched and 2× data-ladder controls are pending. g1i, the same plain hnt40k at g1d's 348.35M train bytes (9.350e15 train FLOPs), scored 1.211442 ± 0.003395 (seeds 1.210431, 1.215228, 1.208666). That is 0.017287 above g1d (p 0.0094), so at equal bytes plain hnt40k loses to struct32k. g1i and g1d use different tokenizers, so this is a tokenizer contrast, not a structure ablation. A3, the random-cluster control (hnt40k with random clusters, FLOPs-matched), finished as g1j: 1.176685 ± 0.002032 (n=3). That is 0.002369 above g1g (Welch two-sided p 0.17). It is not a clean contrast, because spectral init was on in g1g and off in g1j. Untested. Caveats: n=3, one model size, WikiText-103 only. Parameter totals are verified against the per-seed trainer records (the trainer itself is not in this repository): hnt40k-struct-v2 39,943,040, struct32k 23,204,736, and plain hnt40k 25,981,824, each with 10,621,824 non-embedding. Every run applied RoPE. The trainer's structured model path applies RoPE only and ignores --pe heat, so no heat positional encoding has been tested. G1c does not reverse the G1 or G1b failures.

Decide

Publish the harness and the recorded metadata. Do not publish a claim that G1 or G1b beat struct32k. Do not publish the G1c pass as a per-byte modeling win. Do not publish the g1g win without its data-exposure caveat. Do not publish weights or a tokenizer table to support a claim that is not in the ledger.

Act

Keep experiments on iter/<id> branches. Published records: iter/g0 (G0 partial), iter/g1-hnt64k (G1 fail), and iter/g1b-structured (G1b fail on BPB). G1c, g1d, g1g, g1h, and g1i are recorded in this briefing. g1d through g1i have folders under iterations/ on main. A later pilot that wants to clear G1 has to beat struct32k on test BPB and on train FLOPs per byte, with the equal-size control, three seeds, and raw test bytes. Clearing that line on a longer byte budget is a compute comparison. g1d is the equal-data check, and it goes the other way.

1. Situation

The repository is the verification harness for this line of experiments. A trainer elsewhere registers the bytes it used. The store hashes them, appends gate decisions to a ledger, and lets a reviewer recompute the hashes. The synthetic study under fixtures/passing exercises every gate with toy numbers. Passing that study means the checker runs. It does not mean a research arm won.

Friendly constraints: PolyForm Noncommercial 1.0.0, no commercial use without a separate license, contact via GitHub @ZuluYokohama. The tree must stay free of weights, corpus bytes, tokenizer merge tables, credentials, and machine paths.

2. Mission

Make each later claim auditable against the same artifact hashes the gate saw, and keep the public status honest: G0 partial, G1 fail, G1b fail, G1c pass only as compute-matched, g1d lower for struct32k at equal data, g1g lower than g1d at equal analytic FLOPs only, struct-v2 worse than plain hnt40k at equal data and about 3× slower on wall clock, wall-clock and 2× data-ladder controls pending, everything else not run.

3. Execution

Gates are a dependency graph. A gate passes only when its own criteria pass and every upstream gate has a passing ledger record bound to the current hashes. run still writes failures.

Seed minima are per gate. Pilots use 3. The headline uses 5. A study cannot write a smaller minimum into its metrics and have the checker accept it.

Three comparisons are marked on the control graph. hnt vs equal-size control is hnt64k against sw64k. best arm vs struct32k / GPT-2 is the matched-byte and matched-FLOP comparison, on G1, H1, and G4. pe_heat vs baseline is the heat and heat+RoPE positional encodings against the tuned modern baseline, on P2. Marking them does not mean this campaign passed them.

4. Sustainment

The checker does not train, does not launch a kernel, and does not recompute a loss from hidden weights. It recomputes hashes, the ledger, and the arithmetic of submitted seed lists. A convincing trace can still be invented. An independent rerun is the check that the named code produced it.

The seal is HMAC-SHA256. Someone who holds the key can write another chain that verifies. After verify, sheaf-verify anchor prints the ledger head so it can be copied by hand or into a file outside the store. That command does not call an external service.

What this repository spends: a small synthetic fixture and one metadata record. It does not spend a GPU budget, and it does not store the bytes a GPU would have written.
