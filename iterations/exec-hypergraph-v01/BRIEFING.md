# Briefing — exec-hypergraph-v01

## OODA

### Observe

The requested redesign needs executable state and faithful computation records before a learned graph-native interface can be meaningfully assessed. The existing repository stores verification machinery and campaign records; it does not contain the production trainer. This iteration implements a separate reference runtime and bounded byte-span interface.

### Orient

This is an engineering iteration. It speaks to its own documented command semantics and integrity controls. It changes no existing campaign gate verdict and makes no trained-model or tokenizer-superiority claim.

### Decide

The recorded symbolic semantics and replay controls pass; the same semantic answers are achieved by competent conventional evaluators. The initial audited Python implementation is substantially slower than the cached-DAG baseline. That comparison has unequal audit obligations and establishes no architectural speed or capability advantage.

### Act

Use the reference semantics as an integration contract. Next isolate audit overhead with a matched-audit baseline and incremental state commitments, then test a learned action policy on held-out compositions. Preserve the current implementation and measurements as the engineering reference.

## 1. Situation

The user requested an order-of-magnitude capability advance with reduced opacity through a complete redesign. This prototype establishes the formal execution and representation boundaries needed to test that direction. Frozen T-38 and the killed packing experiment remain outside scope.

## 2. Mission

Implement and test reversible byte/span representation, typed scoped state transitions, actual execution traces, intervention controls, and independent conventional baselines before attempting a learned-model capability claim.

## 3. Execution

Read `MODE_METHOD.md`, `spec/IMPLEMENTATION.md`, and the unchanged `spec/PREREGISTRATION.json`. The original specification was recorded before the relational pilot results. Engineering controls added during implementation are documented in `spec/AMENDMENTS.md` and `spec/REVIEW.md`.

The fixed relational grid contains five synthetic workload seeds and four depths. It yields 66 scenarios and 5,992 expected command outcomes per implementation. Eight paired interventions are checked in each of three arms. Actual kernel histories are re-executed for all scenarios. Separate unittest controls cover malformed inputs, limits, revision, scope, source integrity, semantic forgery, byte-prefix causality, and evaluator rejection of deliberately false expected results.

`results/confirmation/` contains the run manifest, exact outcomes, intervention results, raw timings, memory observations, and report. `results/demo/` contains a small transfer/revision/branch demonstration and actual receipts. `results/development/` preserves an earlier development run under its own source hashes.

## 4. Sustainment

Runtime and prototype tests use Python's standard library. Execution was CPU-only in the session environment. No user-workstation or GPU performance is implied. No weights, private corpus, tokenizer merge table, or production trainer configuration is included.

The prototype logs and hashes full semantic state; the conventional baseline omits equivalent audit records. The instrumentation profile identifies state-commitment work as a major current cost. Costs are reported descriptively, with no superiority p-value.
